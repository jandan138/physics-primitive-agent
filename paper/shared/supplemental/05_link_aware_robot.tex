\section{Link-Aware Robot Package Semantics}

Robot assets introduce a constraint that rigid props do not have: primitive geometry must preserve
link ownership. A visually plausible whole-robot package is not enough. If a primitive spans a
joint or attaches to the wrong Newton body, the package can corrupt the robot's articulation even
before any contact task begins.

\paragraph{Link graph.}
Let the source robot link graph be $L=(V,E)$, where $V$ are links and $E$ are joints or kinematic
edges. Each source shape $s\in S$ has an owner map $\lambda(s)\in V$. A generated primitive
inherits its owner from the source support set:
\[
  \ell_i = \lambda(S_i),
\]
where $S_i$ is the source shape subset used by primitive $p_i$. If $S_i$ contains shapes from more
than one link, the package records a cross-link merge risk rather than silently attaching the
primitive to one body.

\paragraph{Cross-link merge predicate.}
The attachment predicate for a generated robot package is
\[
  V_{\mathrm{merge}}(p_i) =
  [a(p_i) \neq b_{\ell_i}] \lor [|\lambda(S_i)| > 1].
\]
The first term catches wrong body attachment. The second catches a primitive whose source support
already spans multiple links. A package passes the structural link gate only when
\[
  \sum_i V_{\mathrm{merge}}(p_i)=0.
\]
This is a structural audit, not a manipulation result.

\paragraph{What this shows.}
Figure~\ref{fig:supp-franka-link-frames} shows the ownership rule that makes robot packages
different from rigid prop packages. The primitive's frame and body attachment must agree with the
source link identity.

\paragraph{What this does not show.}
The figure does not claim whole-robot collision quality, robot manipulation performance, or broad
articulated-dynamics validity.

\paragraph{Generated-package consumption.}
After the link gate, the checker must verify that the generated package is what the runtime
actually consumes. Let $n_{\mathrm{src}}$ be the number of remaining source collision shapes,
$n_{\mathrm{miss}}$ the number of generated primitives whose owning body was missing, and
$n_{\mathrm{filter}}$ the number of generated self-collision filter pairs installed for the smoke
configuration. The package-consumption gate has the schematic form
\[
  A_{\mathrm{consume}} =
  [n_{\mathrm{src}}=0] \land [n_{\mathrm{miss}}=0]
  \land [n_{\mathrm{filter}}\ \text{recorded}].
\]
The generated self-collision filter count is not a quality score. It is evidence that the smoke
configuration accounted for generated package pairs explicitly.

\paragraph{What this shows.}
Figure~\ref{fig:supp-generated-package-consumption} teaches the bookkeeping step between package
generation and robot task smoke. It helps reviewers check that the generated shapes, not stale
source collision shapes, are entering the diagnostic scene.
The practical audit order is: first check that every generated primitive has a target body; next
check that source collision shapes were suppressed; then check that generated self-collision filter
pairs were counted under the smoke configuration; only after those accounting checks should the
hold or trajectory outcome be read. This order prevents a visually plausible robot scene from
masking a stale source-shape path.

\paragraph{What this does not show.}
The figure is not contact-operation evidence and is not deployment readiness for a robot
application. It also does not calibrate self-collision behavior. The filter count is useful because
it records that generated pairs were handled explicitly in the smoke scene, but a contact-operation
claim would require separate robot tasks and additional records.

\paragraph{What this does not show.}
The plate does not imply calibrated self-collision behavior or whole-arm manipulation validity.
