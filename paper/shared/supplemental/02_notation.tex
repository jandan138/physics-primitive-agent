\section{Notation and Package Model}

The main paper describes a four-stage loop: source asset intake, primitive candidate generation,
Newton diagnostic execution, and accept/fallback reporting. This section makes the hidden objects
explicit. We write an input asset as a tuple
\[
  A = (U, S, G, L, M),
\]
where $U$ is the stage or asset identifier, $S$ is the set of source shapes, $G$ is optional render
or visual geometry, $L$ is an optional link graph, and $M$ is metadata such as units and source
provenance. The representation mirrors the need to keep geometry, link ownership, and evidence
records separate when moving assets into Newton~\cite{openusd2026,newton2026}.

A candidate primitive is
\[
  p_i = (k_i, F_i, T_i, \theta_i, \ell_i),
\]
where $k_i$ is the primitive kind, $F_i$ is the source frame, $T_i \in SE(3)$ is the primitive
transform, $\theta_i$ stores dimensions and material-side metadata, and $\ell_i$ is the owning
link identity when the source asset is articulated. The candidate package emitted by generator lane
$g$ is
\[
  P_g = \{p_i \mid i \in I_g\}.
\]
The package is still a candidate at this point. It is not accepted until a configured diagnostic
scene $D$ maps $P_g$ into Newton bodies, runs the probes, and emits an auditable outcome.

\paragraph{Attachment map.}
Let $B=\{b_1,\ldots,b_m\}$ be the simulated body set. For a rigid object, all primitives can map to
one body, so $a(p_i)=b_A$ is usually sufficient. For articulated assets, the link identity must be
preserved:
\[
  a(p_i) = b_{\ell_i}.
\]
This equality is structural, not visual. A primitive that looks plausible in a whole-robot overlay
can still be invalid if it attaches geometry from one link to a neighboring body. That is why the
supplement later defines the cross-link merge predicate explicitly.

\paragraph{Candidate generation versus acceptance.}
The generator lane $g$ can be a bounding primitive, a CPD-style package, CoACD, V-HACD, a native
primitive routine, or a manual package~\cite{cpd2026,coacd2022,vhacd}. The diagnostic layer does
not assume that one lane is always best. It asks a narrower question:
\[
  \operatorname{accept}(P_g,D) =
  \begin{cases}
    1, & \text{if every required predicate in }D\text{ accepts},\\
    0, & \text{if any required predicate emits a failure label}.
  \end{cases}
\]
Fallback is different from failure. A fallback means the lane did not provide an executable package
for a configured probe or was routed away by policy. A failure means the package existed, mapped
into Newton, and was rejected by a named probe.

\paragraph{Outcome vocabulary.}
The supplement uses the same outcome names as the main paper, but separates their semantics:
\[
  o(D,P_g) \in
  \{\mathrm{accept}, \mathrm{failure}, \mathrm{fallback},
  \mathrm{not\ applicable}, \mathrm{dependency\ gap}\}.
\]
The distinction matters in review. A dependency gap says a required tool or asset was unavailable.
A not-applicable label says the probe was not meaningful for that asset class. A failure says the
runtime task executed and rejected the package. A single success rate would hide these categories,
so the paper keeps them visible.

\paragraph{Reading note.}
Figure~\ref{fig:supp-candidate-lane-anatomy} illustrates the most important bookkeeping rule in
the paper: candidate generation is not acceptance. A generator lane can produce a package with a
reasonable primitive count and still be rejected later by drop/settle, stack-or-slide, sphere-rain,
or robot package-consumption probes.
The figure is not a method comparison and is not evidence that one candidate lane is broadly
superior. It explains the accounting path that keeps fallback and failure from being merged into
one ambiguous label.
